# 第十步：CI 与业务落地

## 目标

把前九步的东西装进 Docker + Jenkins 跑起来，并落地第一个真实业务接口用例。这是从"框架"变成"项目"的关键一步。

## 步骤

### 1. 编写 Dockerfile

```dockerfile
FROM python:3.11-slim

# 换国内源加速
RUN sed -i 's/deb.debian.org/mirrors.aliyun.com/g' /etc/apt/sources.list.d/debian.sources

WORKDIR /app

# 安装 uv
COPY --from=ghcr.io/astral-sh/uv:0.12.5 /uv /usr/local/bin/uv

# 先复制依赖文件，利用 Docker 缓存层
COPY pyproject.toml uv.lock ./
COPY .python-version ./

ENV UV_DEFAULT_INDEX=https://mirrors.aliyun.com/pypi/simple/
RUN uv sync --frozen --no-dev

# 不复制业务代码，代码由 Jenkins checkout scm 拉取
```

要点：依赖提前打进镜像，CI 每次只拉代码，不用重复装依赖。

### 1.1 编写 .dockerignore（docker build 前必须建）

不加 `.dockerignore`，docker build 会把 `.venv`（100+MB）、`.git` 等大目录传进 build context，构建慢还容易误复制：

```dockerignore
# Python
.venv/
__pycache__/
*.py[cod]

# git/IDE
.git/
.dsh/
.history/
.idea/
.vscode/

# 测试产物
reports/
logs/
.pytest_cache/
.mypy_cache/
.ruff_cache/
.coverage

# 环境（真实凭据不进镜像）
.env
.env.*
!.env.example

# 测试数据（敏感）
data/

# 其他
node_modules/
dist/
build/
```

### 2. 编写 Jenkinsfile

```groovy
pipeline {
  agent { docker { image 'registry/pytest-automation/runner:v1.0.0'; args '--network host' } }
  options { timeout(time: 30, unit: 'MINUTES'); disableConcurrentBuilds() }

  parameters {
    choice(name: 'TEST_SUITE',
           choices: ['smoke', 'regression', 'all'],
           description: 'smoke=冒烟 | regression=冒烟+回归 | all=全量')
  }

  environment { CI = 'true' }

  stages {
    stage('Setup Environment') {
      steps {
        sh 'ln -sf /app/.venv ./.venv'
        withCredentials([file(credentialsId: 'api-auto-env', variable: 'ENV_FILE')]) {
          sh 'cp $ENV_FILE .env'
        }
      }
    }
    stage('Run Tests') {
      steps {
        script {
          def f = ''
          switch (params.TEST_SUITE) {
            case 'smoke': f = '-m smoke'; break
            case 'regression': f = '-m "smoke or regression"'; break
            case 'all': f = ''; break
          }
          sh "uv run pytest ${f}"
        }
      }
    }
  }
  post {
    always {
      junit testResults: 'reports/junit.xml', allowEmptyResults: true
      archiveArtifacts artifacts: 'reports/pytest-html/**', allowEmptyArchive: true
      sh 'rm -rf reports/ .pytest_cache/'
    }
  }
}
```

要点：
- `TEST_SUITE` 只保留 smoke/regression/all 三档（对应标记体系）
- `.env` 从 Jenkins Secret 凭据注入，不进仓库
- `post.always` 里清理 `reports/`，避免残留污染下次报告

### 3. 落地第一个真实业务接口（最关键）

按「清单 → 封装 → schema → 契约用例 → 跑通」五步走（以 testing-online 登录接口为例，其他接口实战时按需照做）：

```bash
# ① 从接口清单确认一个接口：登录（POST /api/auth/login）
# ② 封装
#    apis/auth.py:
#      class AuthApi(BaseApi):
#          def login(self, username, password):
#              return self.client.post("/api/auth/login", json={"username": username, "password": password})
# ③ schema
#    schemas/auth.py:
#      class LoginResponse(BaseModel):
#          success: bool
#          message: str
#          data: LoginData | None = None
# ④ 契约用例
#    tests/contract/test_login.py:
#      @pytest.mark.smoke
#      def test_login(http_client):
#          api = AuthApi(http_client)
#          resp = api.login("炊烟1号", "admin123")
#          assert resp.status_code == 200
#          LoginResponse.model_validate(resp.json())
# ⑤ 填 .env 的 BASE_URL=https://testing.yychuiyan.com，跑通
```

```bash
cp .env.example .env.test
# 编辑 .env.test 填 BASE_URL、账号密码
APP_ENV=test make smoke
```

### 4. 失败通知（可选，企业级常配）

测试挂了要主动推送，不能等人工点开报告。最简单在 Jenkins 的 `post.failure` 里打 IM webhook：

```groovy
post {
  failure {
    withCredentials([string(credentialsId: 'feishu-webhook', variable: 'HOOK')]) {
      sh '''
        curl -s -X POST "$HOOK" \\
          -H "Content-Type: application/json" \\
          -d '{"msg_type":"text","content":{"text":"API 自动化测试失败"}}'
      '''
    }
  }
}
```

要点：
- webhook 地址放进 Jenkins 凭据（Secret text），用 `withCredentials` 注入，别硬编码进 Jenkinsfile
- 飞书 / 企微 / 钉钉的 webhook 格式略有差异，但都是"POST 一个 JSON"，套这个骨架即可

## 验证

跑通第一个业务用例，`make smoke` 不再是 skip，而是真实的 passed。

## ⚠️ 常见坑

1. **镜像要先构建推送**：`Jenkinsfile` 里的 `runner:v1.0.0` 得先 `docker build` + `docker push`，否则流水线拉不到镜像。
2. **`--network host` 只在 Linux 生效**：内网环境直连宿主机网络用，macOS 上 Docker 行为不同，别照搬。
3. **多环境在 CI 里用参数 + 多份凭据**：`api-auto-env-test` / `api-auto-env-prod` 分开，加 `TARGET_ENV` 参数选择注入哪份。
4. **空档位 exit code 5 会让流水线失败**（第七步提过）：保证每个暴露的 `TEST_SUITE` 档位至少有一条用例命中。
5. **加解密/认证链路一定要真实跑通一次**：工具齐了不代表对，只有第一条业务链路跑通，才能证明 AES、token 注入、schema 校验整条链是正确的。

### 5. 项目 README（交付文档）

框架搭完，最后补一个项目根的 `README.md`，让新成员「clone 后照着跑」就能上手：

```markdown
# pytest-automation

接口自动化测试框架（pytest + requests），基准项目 [testing-online](https://testing.yychuiyan.com)。

## 快速开始

uv sync                      # 安装依赖
cp .env.example .env.test    # 配置环境（填 BASE_URL、账号密码）
make test                    # 全量测试
make smoke                   # 冒烟测试

## 常用命令

make test        # 全量
make unit/contract/integration   # 按层
make smoke/regression            # 按档位
make lint/format/type            # 质量检查

## 目录结构

core/      框架核心（配置/日志/HTTP/断言/加密/数据生成）
apis/      接口封装（按业务模块）
schemas/   pydantic 响应模型
tests/     unit / contract / integration 三层用例
data/      测试数据（不提交 git）
reports/   报告产物
```

要点：README 是「交接文档」——新成员不读手册也能靠它 + `make help` 快速上手。

## 收尾

至此，一个完整的企业级接口自动化工程就搭好了。回顾整个手册的关键心法：

- **工程化是地基**（1~9 步），**业务用例才是房子**（第 10 步）
- 判断"成熟"的标准不是有多少工具，而是**换个人能否靠 `apis/ + schemas/ + tests/` 直接读懂并回归所有核心接口**
- 每一步都「做完就验证」，别攒到最后一起调试
